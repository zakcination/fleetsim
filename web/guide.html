01

The tick loop

fleetsim is a discrete-time simulation. Time moves in ticks of one second. In one tick a robot either moves to a neighbouring cell or waits. Each run is 10 minutes of warm-up plus one measured hour, so 4,200 ticks. Every tick runs the same five steps:

orders.py

New orders arrive

A random number of orders, from a Poisson stream. Each says "bring pod p to station s, then put it back".

allocation.py

Match robots to orders

Free robots get pending orders: greedy every tick, or Hungarian every 5 ticks.

planner.py

Book a route

Space-time A* books the whole errand, avoiding every route already booked.

sim.py

Everyone steps

Each robot follows its booked route: one cell forward, or a wait.

analytics.py

Log a row per robot

Position, state and order go into the tick log, then into SQLite and Parquet.

An errand is the robot's whole job for one order: drive to the pod, lift it (2 s), drive to the station, wait while a worker picks items (10 s), drive back, put the pod down (2 s), then go home and park. This is the goods-to-person model Amazon Robotics (formerly Kiva) made famous. Shelves come to the picker instead of the picker walking the aisles.

02

The warehouse as a graph

The floor comes from the League of Robot Runners (LoRR), a yearly competition for lifelong multi-robot planning. Its map file is a grid of characters:

@ shelving, can't drive through . open floor S service point = one pod's storage slot E emitter = pick station

fleetsim cuts a 72 × 99 block from the 140 × 500 map. It has 4,109 drivable cells, 2,920 pod slots and 19 stations on the left wall. Each drivable cell is a node. Two nodes share an edge if they touch up, down, left or right. That is a 4-connected grid graph, and every planning question becomes a graph question.

Distance means path length

Two cells can be close as the crow flies but far apart if a shelf row sits between them. fleetsim measures distance with breadth-first search (BFS): start at a cell, label its neighbours 1, their unlabelled neighbours 2, and so on outward. A full sweep of this map takes about 3 ms in Python. The result is a distance field: the true travel time from any cell to that cell. Grid.dist_to keeps the last 2,048 fields in an LRU cache, because the same stations and pods come up again and again. Toggle "Show distance field" in the demo in chapter 05 to see one.

Homes must not wall anyone in

An idle robot parks on its home cell and stays there, so other robots treat it as a wall. choose_parking only picks open-floor cells away from stations. It accepts a cell only if blocking every chosen home still leaves the rest of the floor connected, which it checks with BFS. As a result every pod and station stays reachable however many robots are parked.

03

Orders and load

Orders arrive as a Poisson process with rate λ (orders per second). Think of it as an independent, slightly loaded coin flip every instant. Arrivals are memoryless: a busy minute doesn't make the next minute quieter. The count in one tick is Poisson-distributed with mean λ, and the gaps between orders are exponential. OrderStream.arrivals draws rng.poisson(rate) once per tick.

Offered load ρ

How busy is the fleet? Compare the work arriving with the work the fleet can do:

ρ = λ × (mean errand time) / N robots

fleetsim picks λ from ρ. It estimates the uncongested errand time by sampling 300 random errands with BFS distances (estimate_cycle_time). At ρ = 0.85 robots are busy about 85% of the time and the queue stays short. At ρ = 1.3 work arrives 30% faster than the fleet can finish it. Queueing theory says that queue never settles: it grows roughly in a straight line, forever. That's why the wait times at load 1.3 in the README depend on run length. Try it with ten robots below.

04

One robot: A*

For a single robot, the shortest path is a classic search problem. A* expands cells in order of

f(n) = g(n) + h(n)
  • g(n): cost so far, i.e. steps taken from the start.
  • h(n): an estimate of the steps still needed. A* returns an optimal path if h never overestimates. Such an h is called admissible.

fleetsim uses the BFS distance field from chapter 02 as h. It's the exact remaining distance with no other robots around, so it's admissible and as tight as possible. With a perfect heuristic A* barely explores sideways: it walks straight down the gradient. Other robots then become the main reason it has to search wider.

Why not stop here?Plan every robot with plain A* and they ignore each other. Two robots will reach the same cell at the same second, or swap places through each other in an aisle. The first demo mode in chapter 05 does exactly that so you can count the crashes.
05

Many robots: MAPF

Multi-agent path finding (MAPF): give every robot a path so that no two collide. Planning all robots jointly is exact, but the joint state space grows exponentially: 100 robots on 4,109 cells is hopeless. Practical systems decompose the problem. fleetsim uses the most common decomposition: prioritized planning with space-time A*.

Two ways to collide

Add time as a third axis

Plain A* searches over cells. Space-time A* searches over (cell, tick) pairs and adds one extra move: wait, which stays on the cell and advances the tick. To know which (cell, tick) pairs are taken, it reads a reservation table:

  • vertex entries: (cell, t) → robot
  • edge entries: (from, to, t) → robot, for a move during t → t+1. Before moving a → b, the planner checks for (b, a, t), which would mean a swap.
  • park entries: cell → (robot, from tick) for a robot that stops there for good

Prioritized planning

Plan robots one at a time. Each new robot treats every booked route as a moving obstacle. In fleetsim the priority order is simply the order in which robots get orders. Three rules make it safe in a warehouse that never stops (lifelong MAPF):

  1. Book the whole errand at once: pod, dwell, station, dwell, pod, dwell, home (plan_errand). For a dwell, the goal cell must stay free for the whole lift, pick or drop.
  2. Every robot always holds a plan that runs forever: its booked route, then parked on the last cell. A parked robot has to arrive after the last tick anyone else is booked on that cell.
  3. If the search fails, keep the old plan. The old plan was conflict-free and still is, so the robot keeps waiting at home and the order goes back in the queue.

Together these make collisions impossible by construction: nothing ever enters the table unless it avoids everything already there. fleetsim still checks independently. find_conflicts re-reads the logged positions, and the tests run it on whole simulations. All 12 benchmark runs, 2.7 M robot-ticks, came back clean.

The catch: incomplete

Prioritized planning can fail even when a solution exists. Say a high-priority robot parks at the end of a dead-end aisle that a lower-priority robot needed to get through. The low-priority robot can't change the earlier booking, so it finds no route. Try "New scenario" a few times: now and then a robot shows no route. In fleetsim 0–2% of errand plans fail this way and are retried a few ticks later. Stronger methods search over priority orders (Priority-Based Search, PBS), replan in rolling windows (RHCR, used for lifelong warehouses), or use rule-based solvers built for thousands of agents (PIBT, LaCAM). Those are roadmap items.

06

Who fetches what

With several free robots and several waiting orders, which robot takes which order? This is the assignment problem. Build a cost matrix C where C[i][j] is the BFS travel time from robot i to the pod of order j. Then choose pairs, each robot and each order used at most once, to keep total travel low.

  • Greedy, first come first served (GreedyAllocator): every tick, take the oldest order and give it the nearest free robot; repeat. It's fast and fair to old orders, but an early choice can grab a robot that a later order needed more.
  • Hungarian (HungarianAllocator): find the assignment with the minimum total cost. Kuhn published it in 1955. It runs in O(n³), and SciPy exposes it as linear_sum_assignment, which also handles rectangular matrices. fleetsim re-solves every k = 5 ticks over the oldest 2 × (free robots) orders.

What the benchmark found

At load 0.85 the two policies tie (122 vs 122, 658 vs 651, 1,335 vs 1,340 tasks/h). There's rarely more than one order waiting, so there's nothing to optimise, and Hungarian adds about 2 s of latency because it batches. At load 1.3 Hungarian completes 16–20% more (100 robots: 1,619 → 1,892 tasks/h), and three seeds agree.

The catchWith a backlog, Hungarian also decides which orders get served, and minimising travel favours orders whose pods sit near free robots. That works like "shortest job first", a different queue discipline. Greedy here is first come first served. So part of the +17% is a fairer-vs-faster trade-off, not pure optimisation. Look for it in the backlog scenario above: optimal tends to skip a far-away old order. The fair test for v0.2 adds a greedy "nearest order for each free robot" baseline.

Measuring the fleet

All KPIs are computed over the measured hour only. The 600-tick warm-up is skipped so the empty start doesn't flatter the numbers. Example values: 100 robots, greedy, load 0.85.

Sanity check with Little's law

For any stable system, L = λ W: items in the system = arrival rate × time each one spends inside. It holds whatever the arrival or service distributions are, which makes it a great check on a simulator.

λ = 1,335 / 3,600 = 0.371 orders/s · W = 193 s mean lead time → L ≈ 71.6 orders in progress

Utilization says 70.7 of 100 robots are on an order at any moment, and each busy robot carries exactly one order. 71.6 vs 70.7: the bookkeeping holds up. The small gap is mostly time-to-assignment and edge effects at the window boundary.

Censored waits and survivorship bias

Averaging wait time over completed orders rewards a policy that never serves its hardest orders, because those never complete and never count. fleetsim counts every order created in the window. An order still unassigned at the end counts with the wait it has built up so far. Statisticians call this a censored observation. In credit-risk terms it's the same as keeping loans that haven't defaulted yet in the denominator.

Two kinds of congestion

Travel-wait counts the moments a robot stands still. Congestion delay also counts detours, since a robot that goes around a jam never stops but still arrives late. At 100 robots both are small here (≤ 3%, 7–10 s on a ~190 s errand). This map isn't crowded at 2.4% density. The notebook's heatmap shows where the waits cluster: the left-wall corridor in front of the stations.

08

From ticks to SQL

The log is one row per robot per tick, the finest grain available. Every KPI is an aggregate of that grain, so you can always re-derive a number and never depend on a pre-computed summary. Same principle as keeping loan-level data instead of only portfolio totals.

TableGrainKey columns
runsone simulationn_robots, allocator, load, rate_per_tick, warmup, ticks
ticksrobot × ticktick, robot, row, col, state, moved, waiting, order_id
ordersordercreated, assigned, picked, at_station, serviced, completed, free_flow (−1 = not yet)
plansplanner calltick, robot, ms, ok, expansions, n_pending

SQLite for ad-hoc SQL with zero setup; Parquet (columnar, compressed) for pandas, DuckDB or Spark later. The same data is 250 MB as SQLite and 7 MB as Parquet. That gap is why columnar formats rule analytics. Utilization and travel-wait per run, in one query:

SELECT r.n_robots, r.allocator, r.load,
       AVG(t.state IN ('to_pod','lift','to_station','service','return','drop')) AS utilization,
       1.0 * SUM(t.waiting)
           / SUM(t.state IN ('to_pod','to_station','return'))                    AS travel_wait_share
FROM ticks t JOIN runs r USING (run_id)
WHERE t.tick >= r.warmup AND t.tick < r.warmup + r.ticks - 1
GROUP BY t.run_id;

In SQLite a comparison returns 0 or 1, so AVG(condition) is a share and SUM(condition) is a count. The notebook builds every README KPI this way. The SQL and Python numbers match exactly, a useful cross-check.

09

What v0.1 shows, and what it doesn't

  • Shows: zero collisions in every run, checked independently of the planner that produced them.
  • Shows: throughput grows almost linearly from 10 to 100 robots on this map. 100 robots here is not congestion-bound.
  • Shows: assignment only matters when there's a backlog to choose from.
  • Doesn't show: behaviour at realistic density. Amazon floors run far denser than 2.4%. Next stress test: 200–400 robots on a tighter crop.
  • Doesn't show: that Hungarian beats a smarter greedy. The queue-discipline confound in chapter 06 is still open.
  • Doesn't show: steady-state waits at load 1.3, which don't exist when ρ > 1 (chapter 03).
  • Simplified: no turning time, acceleration, execution delays or battery. Pods aren't physical obstacles while carried. Single map, single crop.
10

Interview drill

Answer out loud first, then open the card.

Why can't each robot just run A*?

A* plans for one agent in a static world. Robots are moving obstacles for each other. Independent paths collide (vertex conflicts) or pass through each other (swap conflicts). Planning all robots jointly is exact but exponential in the number of robots. MAPF methods sit in between.

Walk me through space-time A*.

The search state is (cell, tick), and "wait" is a legal move. A successor is valid if no other robot holds that (cell, tick), no robot is crossing the same edge the other way, and no parked robot sits there. The heuristic is the BFS distance to the goal, which ignores other robots so it never overestimates. For the final parking goal, arrival must come after the last tick anyone else uses that cell.

Is prioritized planning complete? Optimal?

Neither. Fixed priorities can rule out every solution, for example an early robot parking in a dead end a later robot must pass. Each robot gets an optimal path given the earlier bookings, but the fleet total isn't optimal. It's used because it's fast, simple and works well at moderate density. Fixes: search over priorities (PBS), random restarts, windowed replanning (RHCR), or PIBT/LaCAM at very large scale.

How do you know there are zero collisions?

Three layers. (1) Invariant: the table only accepts routes that avoid all current bookings, and a failed search keeps the old, still valid, plan. (2) An independent checker re-reads logged positions for vertex, swap, teleport and obstacle violations; it shares no code with the planner. (3) Unit tests cover each conflict type plus whole simulations with both allocators.

Greedy vs Hungarian: when does it matter?

Only when there's a choice, i.e. several free robots and several pending orders. At load 0.85 they tie. With a backlog Hungarian wins about 17% on throughput, but part of that is that it serves nearby orders first, which hurts fairness: its worst wait is sometimes longer. I'd report a tail-latency metric next to throughput and add an aging penalty if fairness matters.

Why log every tick instead of just KPIs?

Grain. With robot × tick data you can recompute any KPI, slice by region (congestion heatmap), audit odd numbers, and run checks like Little's law. Summary-only logging locks in today's questions. Parquet keeps it cheap: 7 MB for 2.7 M rows.

What would you change to run this for real?

Move the planner core to C++ (10–100× faster) behind ROS 2 action servers. Plan in rolling windows so robots can replan when delayed. Add execution-delay handling (LoRR models random delays). Use a smarter dispatcher with aging. Validate against Gazebo/Isaac physics before hardware.
